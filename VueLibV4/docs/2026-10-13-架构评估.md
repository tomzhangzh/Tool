# VueLibV4 低代码平台 技术架构评估（2026-10-13）

> 评估日期：2026-10-13
> 评估对象：VueLibV4（ASP.NET Core 8 + SQLite/SqlSugar + Vue3(全局UMD) + 自研 dyn 运行时）
> 路线定位：**面向 .NET 开发者的混合式低代码快速开发平台**（配置优先、代码兜底，非零代码、非全 JSON Schema）
> 对比基线：docs/2026-10-04-架构评估.md（下称"10-04 评估"）
> 证据约定：本文"现状"仅写可从代码库观测到的事实（文件、代码、SQL、提交记录）；推测与建议单独标注，不作为既成能力。

## 二、10-04 → 10-13 的关键进展（9 天）

### 2.1 ✅ 权限短板实质性补齐（10-04 评分 5/10 的最大失分项）

证据：
- 模型：Platform/Models/PermissionModels.cs —— SysUser / SysRole / SysUserRole / SysResource / SysResourcePermission / ResourceNodeType（用户-角色-资源-授权四层）
- 全局拦截：Program.cs 注册全局 `PermissionFilter`；未登录 API 返回 401、页面跳登录
- 特性体系：Core/PermissionAttributes.cs（资源级 RequirePermission、AllowAnonymousPermission）
- 行级数据权限：IPermissionHook 接口 + DemoRowLevelHook 示例实现（扩展点已留出）
- 对外集成：ApiKeyAuthMiddleware（默认关闭，配置开启后校验 X-Api-Key，本机回环放行，配合转发头中间件防绕过）
- 可观测：ExceptionLoggingMiddleware 异常落 SysLog 表；前端错误有上报端点（AllowAnonymous + 同源校验）
- 前端：dyn-permission.js（151 行）参与 UI 侧权限控制

结论：从"无认证"提升为"**认证 + 资源级授权 + 行级权限扩展点 + API Key + 审计日志**"的完整骨架。仍缺：字段级权限、认证强度控制（默认口令未见强制修改机制、无验证码/登录限流证据）、权限规则的自动化测试。

### 2.2 ✅ "逃生舱"落地：配置 ↔ 手写代码双向通道（战略性进展）

这是本期最重要的架构演进，直接补上了纯配置型低代码的天花板问题：

- PageSetting 新增 GeneratedViewPath（实体 + 建表 SQL + 启动幂等迁移）
- ViewGenerateService：把 ConfigJson 组件树生成为**可手改的真实 cshtml**，生成后回写路径；FilterApp/DetailApp 加载时"有路径走文件、无路径走 JSON 动态渲染"，粒度为逐区块
- 标签命名与运行时注册统一（dyn- + kebab），生成视图与 JSON 动态渲染走同一套组件契约
- DynNodeViewOptions 类 + `new { ... }.ToJson()`：手写选项有 IDE 补全和编译期检查；class 等关键字键自动用字典初始化器；非法标识符键回退 C#11 原始字符串
- _BaseLayout 裸标签可接收 comoptions/labeloptions/itemoptions/wrapperoptions 等属性（对象或 JSON 字符串均可），字符串侧 JSON.parse 失败只 warn 不崩页
- 管理页行操作通用化（rowActions 声明式配置，setting 102 已接入"生成视图"按钮 + 覆盖确认）

意义：平台形成 `可视化设计器 → 标准 cshtml → 程序员自由手改 → 运行时按路径加载` 的完整闭环，且逐页面、逐区块可回退。**这是"玩具低代码"与"生产级快速开发平台"的分水岭能力。**

### 2.3 ✅ 元数据健壮性修复

- 19 个组件（DynSlotHost、DynRpcLoader、DynLookup、DynElUpload 等）补全 PropertyConfigJson；补全逻辑同步进 Data/update-property-config.sql 且带幂等守卫，**全新建库不再丢配置**
- 主子表（Tab）保存链路修复：新增回写主键、子 Tab 解锁、独立 execId 弹层、preFill 外键
- Block 事件词汇收敛：add/newForm 合并为 create、edit 系列合并为 update、saved 单一事件，壳层不再做翻译转发

### 2.4 文档与知识沉淀

docs/ 现有 20+ 份文档：架构评估、PageSetting 设计、多表关联方案、权限使用文档、M1-M4 验收报告、交接文档等。对单人项目而言，文档密度显著高于同类自研系统。

## 四、核心优势（可证据化）

1. **路线差异化真实成立**。市面低代码多为全 JSON Schema 路线，复杂场景天花板明显；本平台"JSON 存组件配置、页面可渲染、可生成、可逃逸到手写代码"的混合路线在 .NET 生态内有清晰生态位，且本期已把最后一环（逃逸后回归）打通。
2. **契约统一度高**。设计器 JSON、运行时 jc、生成视图、裸标签四者共用同一套小写键名契约（comoptions/labeloptions/itemoptions/compassthrough），减少了 N 套映射层。
3. **自研内核有章法**。dyn-kernel 阶段化装配 + requires 声明显式报缺依赖 + PENDING 队列，优于常见脚本堆叠式自研框架；事件总线、RPC、DSL、validator 均为独立小文件。
4. **热反馈开发环极短**。Razor 运行时编译 + 视图不打包 + 免模型 CRUD + 一键三屏生成，作者单人迭代速度被工具链放大——242 次提交、9 天补齐权限与逃生舱即为证据。
5. **调试工具链面向业务人员**。Debug 面板（1,767 行）、组件检查页、Block 消息图、ER 图，降低了配置排错门槛。

## 五、风险与短板（按严重度排序）

### P0 — 规模放大前必须处理

1. **零自动化测试 + 视图不参与编译 = 回归靠人肉**。本期"一个 `@` 让全站组件静默空白"的事故已演示该风险：_BaseLayout 被 72 个组件共享，一处语法错误无任何编译/启动拦截。建议：启动期对全部组件 meta 做一次 define 冒烟（空 template 即告警）；ViewGenerateService.RenderView 是纯函数，最适合先补单测。
2. **巴士因子 = 1（推断）**。提交史与文档风格显示主要为单人开发；知识虽文档化，但 in-DOM 模板 + UMD 全局 Vue + 自研内核的组合非主流，协作/交接成本高。
3. **生成文件与 JSON 双向不同步**。再生成会覆盖手改，目前仅有文件头文字提示，无 hash 校验、无备份、无 diff 确认。一次误点即可丢失定制。

### P1 — 上线/交付前应处理

4. **元数据无缓存**（旧 P1 欠账）：组件清单、PageSetting、DynBlock 每请求查 SQLite。
5. **加载分支膨胀**：JSON 动态 / GeneratedViewPath / PartialPath(Back) / ExtViewPath 四条路径，缺少"一个区块最终渲染什么"的决策图，半年后改动风险高。
6. **权限深度不足**：无字段级权限；默认口令 admin/admin123 未见强制修改策略；登录无限流/验证码证据；DynDiv 调试面板的生产开关与数据隔离需复核。
7. **数据修补靠一次性脚本**：根目录 check_allowcreate.py、fix_duplicate_allowcreate.py、strip_templates.py 等 8 个脚本是手工修库痕迹，说明缺少数据迁移/修复的正式通道。
8. **SQL 注入面需要持续审计**：sqloptions 等接口接受前端传入 SQL 片段。已有项目级控制的迹象，但这类"配置即 SQL"能力必须明确只能被有权限的角色使用，且服务端不得回读执行任意业务库 DDL。

### P2 — 已知取舍，接受即可

9. SQLite 决定部署形态偏向单机/部门级/私有化，不适合多租户高并发云服务——这是定位而非缺陷，但商业化路径要据此选择。
10. 多 UI 栈共存（Element Plus + Tailwind + Layui）的 CSS 污染风险仍在。
11. RuntimeCompilation 在生产环境会带来启动后首次编译开销，并要求服务器对视图目录有写权限之外的文件可读性配置。

## 六、前景判断（分场景，避免笼统乐观）

**1. 作为个人/团队的内部生产力放大器 —— 前景明确看好。**
.NET 后台团队最常见的痛是"简单 CRUD 占 70% 工时，但真要定制时低代码平台反而碍事"。配置优先 + 一键落地为可改 cshtml 的模式精准命中这个区间。以当前工具链完成度，承接部门内部管理系统（数十到数百页面、单组织私有化部署）是现实目标。

**2. 作为私有化交付的低代码产品（中小企业/软件外包商）—— 有机会，差产品化一层。**
门槛不在架构，在：安装包与升级故事（当前靠 EnsureColumn + 手工脚本）、权限深度、示例项目与模板市场、面向非作者的使用文档。这些都是可补的工程项，不需要改架构方向。

**3. 作为 SaaS / 通用低代码平台 —— 不建议。**
SQLite 单库、渲染依赖服务端、in-DOM 模板与全局 UMD 技术栈、无多租户证据，均与云端多租户方向相悖；该赛道也已高度红海。以现有架构追赶成本极高。

**4. 作为开源项目 —— 中性偏乐观。**
混合路线 + .NET 8 + 可视化设计器 + 逃生舱在国内 .NET 开源低代码中辨识度不错；但零测试、单人巴士因子、根目录临时脚本会降低外部贡献者信任，开源前需要一轮"门面清理"（测试骨架、CONTRIBUTING、示例、CI）。

## 七、建议的下一步（按性价比排序）

| 优先级 | 事项 | 理由 |
|---|---|---|
| 1 | 组件 define 启动冒烟 + RenderView 纯函数单测（xUnit 工程） | 以最小成本终结"静默空白"类事故，建立第一个测试工程 |
| 2 | 生成覆盖保护：存文件 hash，手改后再生成需确认/自动 .bak | 逃生舱敢不敢用，全看这一道保险 |
| 3 | 区块渲染决策图固化进 docs（四分支判定顺序+示例） | 防止核心机制随分支增长而失控 |
| 4 | IMemoryCache 包一层元数据读取（组件/Block/PageSetting） | 旧 P1 欠账，改动面小 |
| 5 | 权限收尾：首次登录强制改密 + 字段级权限方案设计（可后置到有真实需求时） | 安全从 7 到 8 的路径 |
| 6 | 根目录 fix_*.py 归档，形成"数据修复脚本"规范目录或并入迁移机制 | 降低仓库噪音与误执行风险 |
| 7 | 手改区域保护（#region 局部保留）或设计器单组件自定义模板入口 | 吃掉逃生舱场景里一半需求，但可等真实使用痛点出现 |

## 八、总评

**VueLibV4 在 2026-10-13 的状态：一个方向正确、工具链锋利、正在从"作者自用框架"过渡到"可交付平台"的混合式低代码系统。综合 85/100（10-04 为 82）。**

分数提升不来自功能数量，而来自两件事：最大的硬伤（无认证）补成了完整骨架；最大的路线疑问（配置碰到天花板怎么办）用"生成可手改视图 + 按路径加载"给出了闭环答案。

**决定它最终落在 85 还是 90+ 的，不再是架构方向，而是四件工程化小事：测试、覆盖保护、缓存、分支收敛。** 这四件都不性感，但正是"我写得很快"与"别人也敢用"之间的距离。
