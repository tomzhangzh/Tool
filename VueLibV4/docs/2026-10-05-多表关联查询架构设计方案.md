# VueLibV4 低代码平台 - 多表关联查询架构设计方案

> 日期：2026-10-05
> 状态：**方案设计，暂不实施**

---

## 一、设计核心思想 & 取舍原则

### 1. 核心定位

**只解决通用简单多表查询、筛选场景，彻底放弃复杂场景全自动兼容。**

严格遵循「**简单场景配置化、复杂场景人工兜底**」的极简架构原则，杜绝框架无限膨胀、逻辑臃肿、坑位无穷的问题。

### 2. 核心取舍（关键架构边界，永久不变）

1. **只做【读操作】，不做任何自动多表写操作**
   - 框架不自动处理多表新增、修改、删除、事务拆分
   - 多表写入全部交给自定义接口 / 人工 SQL

2. **只支持【一级外键关联】**
   - 不支持二级、三级嵌套关联
   - 杜绝无限递归复杂度

3. **不追求万能**
   - 太复杂的场景永远做不完，不做
   - 复杂场景直接走视图 / 手写 SQL

## 二、能力范围

### 要做的（第一优先级）

| 能力 | 说明 |
|------|------|
| 关联字段展示 | 列表自动带出 `Student.ClassId → Class.Name`，显示为 `ClassName` |
| 关联字段筛选 | Filter 组件可以用关联副表的字段做查询条件 |

### 不做的（明确排除）

| 不做 | 原因 |
|------|------|
| 多表自动写入 | 复杂，交给自定义接口 |
| 二级以上嵌套关联 | 复杂度爆炸 |
| 自动生成复杂 Join SQL | 性能不可控 |
| 主从表一对多保存 | 单独讨论，不在本次范围 |

## 三、两套模式并行

### 模式 1：自动关联（简单场景，开箱即用）

依托数据库 ER 元信息（已有 DbErGraph 模块），自动识别主外键关系。

**识别规则：**
1. 优先读取数据库物理外键约束
2. 物理外键不存在时，可选启用命名约定兜底：`ClassId → Class.Id`（可开关）

**工作流程：**

```
列表查询 Student：
  1. 识别 ClassId 是外键 → 关联 Class 表
  2. 查询 Student 分页列表
  3. 批量查询 Class WHERE Id IN (所有 ClassId)
  4. 内存映射 ClassId → Class.Name
  5. 回填 Student 行，字段名 ClassName
  6. 返回前端
```

**优点：**
- 不用 JOIN，分页稳定
- SQL 简单，性能好
- 列表自动多出 ClassName 字段，前端无感知

**Filter 筛选：**
- 设计器里可以选 `Class.Name` 作为筛选条件
- 翻译成 SQL：先查 Class 符合条件的 Id 集合 → `WHERE ClassId IN (...)`

---

### 模式 2：人工兜底（复杂场景）

遇到任何自动关联搞不定的情况：
- 多表复杂 Join
- 多级关联
- 聚合统计
- 特殊业务过滤

**直接建数据库视图，或者手写自定义 SQL。**

视图在框架里等同于一张普通表：
- Filter 复用现有能力
- 列表复用现有能力
- 分页复用现有能力

**框架完全不需要理解视图内部的关联逻辑。**

## 四、边界约定

### 1. Lookup 是只读展示字段

- `ClassName` 只是查询投影，用于展示
- 编辑时只操作 `ClassId`（下拉选择）
- **框架不会修改 Class 表**

### 2. 一级限制

- 只支持 `Student.ClassId → Class.Id`
- 不支持 `Class.MajorId → Major.Id`（二级）
- 二级关联请用视图解决

### 3. 总开关

- 项目级配置可以关闭自动外键解析
- 关闭后框架退回纯单表模式，无额外负担

---

## 五、需要解决的细节问题

| 问题 | 方案 |
|------|------|
| 字段命名冲突 | 投影时起别名：`Class.CreateTime AS Class_CreateTime` |
| 筛选控件类型 | 从关联表字段定义自动推断（字符串→输入框，数字→数字框） |
| 性能 | 加开关，页面可手动关闭自动关联；复杂查询强制走视图 |
| 物理外键缺失 | 命名约定兜底（`XXXId → XXX.Id`），可开关 |

---

## 六、后续落地优先级

1. **第一阶段：关联字段展示** — 列表自动带出外键名称
2. **第二阶段：关联字段筛选** — Filter 支持副表字段查询
3. **第三阶段：设计器支持** — 可视化选关联字段

---

## 七、一句话总结

> 简单场景，依靠数据库主外键元信息，自动带出关联名称，并且支持关联字段筛选；复杂场景直接上视图 / 手写 SQL，复用现有整套 Filter 和列表能力。框架只负责「读」层面的关联展示与筛选，不自动处理多表写入，控制住整体复杂度。
