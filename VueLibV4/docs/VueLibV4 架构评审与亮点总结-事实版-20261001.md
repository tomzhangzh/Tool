# VueLibV4 架构设计与亮点总结（事实核对版）

> 成文日期：2026-10-01
> 本文与《VueLibV4 架构设计与完整亮点总结》并存：那份偏理念宣传，本文只写**对照当前代码核实过的事实**，并对每条能力标注状态。
>
> 状态图例：**【已实现】** 代码中可运行；**【部分】** 主链路可用但有明确缺口（随附说明）；**【规划】** 代码中基本不存在。
>
> 评价口径：以"个人/小团队主导的 .NET 内部开发平台"为基准，不以商业 SaaS 低代码为基准——两者投入量级不同，混在一起打分没有意义。

---

## 一、它到底是什么

一句话：**一个无构建（Razor RuntimeCompilation + Vue3 UMD）、免实体类、声明式动作驱动、支持多独立 Vue App 嵌套装配的 .NET 动态页面引擎。**

核心哲学与原文档一致，且在代码里确实被贯彻了：

> **框架内部承担复杂逻辑，对外尽量属性化、声明式；不强迫单一开发范式——Razor 后端渲染与纯前端配置驱动两条路都能走。**

技术栈：ASP.NET Core MVC（Razor）+ Vue3（UMD，无打包）+ Element Plus + layui（弹窗）+ SqlSugar + SQLite（平台库/业务库可按项目路由）。

---

## 二、整体架构（现状）

动态页面由四层组成，配置与运行时的对应关系如下：

| 层 | 载体 | 职责 | 状态 |
|---|---|---|---|
| **PageSetting** | 库表 | 一个区块的 UI 元数据：ConfigJson 组件树 / DefaultJson 数据骨架 | 【已实现】 |
| **DynBlock** | 库表 + `Views/DynBlocks/Apps/*.cshtml` | 可复用功能单元（筛选/列表/明细），每个是独立 VueApp | 【部分】内置三块可用；按 ViewPath 动态渲染 Block 的通用宿主未做 |
| **DynTemplate / DynTemplateBlock** | 库表 + `Views/DynTemplates/*.cshtml` | 模板外壳 + 槽位关系（filter/list/detail/tree） | 【已实现】 |
| **DynWebPage** | 库表 | 模板实例，参数存 ParamsJson（顶层模板参数 + blocks 槽位分组） | 【已实现】 |

横切能力：

- **dyn-core**：挂载/卸载、多 App 嵌套、片段注入、台账管理、共享 scope；
- **dyn-params（统一参数上下文）**：跨 App/片段/弹窗的参数继承与流动；
- **dyn-action（声明式动作链）**：属性配置交互 + 后端 dyn-actions 下发；
- **数据层**：免 Model 动态 CRUD + 强类型 RPC 能力桥双通道；
- **设计器**：可视化画布 + Markdown 风格 DSL 双模式 + PageGen 三屏自动生成。

架构特点属实：**分层清晰、扩展以横向新增为主；Razor 视图不编译进 dll，前后端共享同一条热重载链。**

## 三、核心亮点（按工程含金量排序，均已核实）

### 1. 多独立 Vue App 嵌套内核【已实现】——全项目最见功力的部分

平台要支持把"自带 app 的 HTML 片段"随时注入页面任意位置（弹窗、tab、行展开），Block 因此必须能脱离任何父级独立存活。dyn-core 的解法是一套完整的挂载协议：

- 子 App 节点先掩码搬入 `#dyn-holder`，原位留 `<dyn-host>` 占位，避免子模板被父 Vue 提前编译；
- 父 App 挂载成功后，**按 uid 重查渲染后的占位符**，`for...of await` 串行还原并递归挂载子 App；
- 并发挂载共享同一个 `__dynMounting` Promise，杜绝重复 createApp；
- 挂载失败 rollback：销毁半成品 app、节点从 holder 还原回占位符；
- 父子关系维护在 App 台账（`__dynChildApps/__dynParentAppEl`），卸载按台账级联——子 App 即使已脱离 DOM（被 Vue patch 抹掉或滞留 holder）也能被清掉；
- 官方注入点 `<dyn-inject-host>`：Vue 不 diff 其内命令式注入的子节点，外层重渲染不会抹掉弹窗/片段内容。

这套机制处理的是嵌套动态注入最容易出的四类事故（孤儿 App、双挂载、异步组件注册竞态、卸载泄漏），且代码注释如实记录了每个坑的成因。**这是从真实故障里长出来的代码，不是从教程里抄得到的。**

### 2. 统一参数上下文 ParamContext【已实现】——解决低代码的老大难

"弹窗、tab、动态片段之间参数怎么流"是所有页面引擎的难题，本项目给出了完整且自洽的答案（`dyn-params.js`）：

- 一套取值语法：模板里 `{{$params.courseId}}`，JS 里 `dyn.params(el).get('courseId')`，动作里 `$params.x / $model.x / $result.x`；
- 多来源按固定优先级就近合并：调用点入参 > 本层运行时覆盖 > 本地静态声明（`data-dyn-params` / `dynparams` 脚本 / Block 的 `data-blk-config`）> 共享实体层 > 本 App model > 父链 > URL query；
- `ctx.fork(el, localParams)`：片段/弹窗挂载点自动派生上下文，父链继承 + 私有层隔离；
- `ctx.commit(key,val)` 共享实体层：链式各 fork、兄弟 tab 立即可见；
- **快照型 vs 跟随型**语义分离：默认挂载时取值；声明 `data-dyn-watch-params` 后参数变化派发 `dyn-param-changed`，由编排方决定是否重载；
- `$result` token 在链路未产生结果时**保留原串**、产生后自动重解析——这个细节体现了对声明式系统"时序大于取值"的理解；
- 后端可通过响应里的 `dyn-actions` 下发 `setparams`（默认写共享层，`scope:'local'` 写私有层），保存后回传新主键无需写回调 JS。

配套约束也立住了：URL 参数全层可见但**不自动随请求发送**，必须显式引用；跨容器流动参数必须用具名实体（courseId），禁止裸 id。

### 3. Block 契约：实例句柄协作，不要全局总线【已实现】

每个 Block 是独立 VueApp，全部输入来自容器单个 `data-blk-config`，无根查找、无轮询。协作只通过容器上的实例句柄 `element.__dynBlock`：

- `send(cmd,payload) → Promise`（编排方下命令，未注册/已销毁则 reject）；
- `on(evt,fn) → off`（订阅事件）、`emit`（Block 内部发事件）、`reg`、`destroy`、`introspect`。

边界纪律清晰且已执行：Block 的 mounted 只做自身初始化、**不发对外事件**（外事件只能由用户交互触发，因此模板 await 挂载完成后再接线必然不丢事件）；Block 不调 `layer.close`、不带 modal 标志、不发 window 事件——保存成功只 emit `saved`，关窗/刷新全部由编排层按三屏或弹窗形态决定。片段注入遵循"谁注入，谁编排"，注入方 scan 句柄自行接线。

> 旧的 message-center 全局消息总线、组合/独立双模式、`data-root-ext-id` 轮询水合机制已整体删除。新代码不得复活。

### 4. RPC 能力桥 + 免模型 CRUD：后端能力开放的双通道【已实现】

- **免模型 CRUD**：知道表名即可分页/增删改查（列全 nvarchar），多库按请求体 `project`（Code/Id）路由，op 过滤 DSL，URL 缺省由控制器/模板自动补齐。复杂业务随时可换自定义 URL，不强制。
- **RPC 能力桥**：前端可直接 `dyn.service('XxxService').Method()` 或 `dyn.eval('C# 表达式')` 调用 DI 中全部注册服务；内置 `Crud / Biz / Platform` 三个变量；强类型实体查询门面 `实体名.Where("x => ...")` 把字符串 lambda 编译成表达式树下推 SQL。

  护栏是认真做过的：选用 DynamicExpresso 而非 Roslyn 脚本（安全面更小）；`Task.WhenAny` 超时赛跑；返回集合 10000 行硬上限；代码长度上限；eval/invoke 双开关；invoke/eval 全量审计日志；JToken→CLR 类型归一化（整数压成 int 避免表达式树类型不一致）。

对 .NET 开发者这是真正的杀手锏：**通用表操作零代码，强类型服务零 Controller 样板**。

### 5. 声明式动作链：JSON / View 片段双通道，后端可零 JS 接管页面区域【已实现】

打开弹窗、postback、确认、刷新、setparams、createapp、evaljs 等均为属性配置，页面基本不写 JS；动作 options 在构建时自动按所属参数上下文解析 token。更关键的是，**后端编排前端行为有两条对等通道，按返回形态自动选择，Controller 全程不写 JS**：

**通道一：JSON 通道（接口返回 ApiResult）**

后端在响应中带 `dyn-actions` 数组即可编排保存后的前端行为（关窗、刷新、回写参数）：

```csharp
return ApiResult.Ok(data).WithActions(
    new FlashMessageJavaScript { Message = "保存成功" },
    new ReloadJavaScript { Selector = "#listPanel" },
    new CloseDialogJavaScript());
```

前端 postback/updateel/reload 收到后统一按序执行；保存接口不需要写任何 JS 回调。

**通道二：View 片段通道（返回 PartialView，MVC 开发者的原生写法）**

- Ajax 身份在 Layout 层自动判别：`_ViewStart.cshtml` 检查 `X-Requested-With: XMLHttpRequest`（`fetchPartial` 请求时固定携带），是 Ajax 就走只含 `RenderBody + Scripts + RenderDynActions` 的 `_AjaxLayout`，否则走完整 `_Layout`。**同一个 Action，整页访问出完整外壳，Ajax 访问只出片段，Controller/View 一行判断都不用写。**
- Controller 里 `this.ExecJS(new ReloadJavaScript { Selector = "#x" })` 注册动作，片段末尾自动渲染为隐藏标记 `<div style="display:none" dyn-init-reload='{...}'></div>`；片段注入页面任意位置后，`initActions` 扫描自动执行。
- 内置服务端动作已覆盖常用场景：FlashMessage / Reload / EvalJS / Redirect / CloseDialog / GridReload。

**片段内容自动判别，后端无需选边**：注入的 HTML 里没有 App 标记就当静态片段渲染；内含 `data-dyn-mode="createApp"` / `data-dyn-init-*` 节点就自动挂载 Vue 实例并自举。于是"给区域一个 URL，这块区域就归后端接管"成为一等用法——

```html
<div data-dyn-init-load='{"url":"/Order/PricePanel"}'></div>
```

后端只当自己在写普通 MVC Partial：想出纯 HTML 就出纯 HTML，想在片段里混 Vue 能力就在 View 里放 App 标记，想在渲染后驱动页面就 `ExecJS`。这是"前后端双范式兼容"最实在、对 .NET 开发者也最有说服力的证据。

### 6. 无构建热重载链路【已实现】——被低估的生产力

Razor RuntimeCompilation（视图不编译进 dll）+ Vue3 UMD（无 webpack/vite）+ 静态 JS 直引。改 cshtml / SQLite / 静态文件刷新即见；只有 C# 实体、Seeder 等改动才需 build 重启。对单人快速验证，这条链路节省的时间远超它带来的"不够现代"的观感损失。本地资源（CodeMirror/ECharts/layui/Emoji）全部内嵌，无 CDN 依赖。

### 7. 积木资产 DB 化 + 参数页一次装配【已实现，运行时消费为部分】

- DynBlock 实体携带稳定 Code、ImplementsRole、ViewPath、ParamConfigJson（参数表单 UI 树）、ParamDefaultJson、Commands/Events 契约；
- DynTemplateBlock 以 `(TemplateId, Slot)` 唯一约束描述槽位；
- DynWebPage.ParamsJson 终态为 `{…模板参数顶层扁平, blocks:{slot:{settingId,model,options}}}`，装配读 blocks 优先、旧扁平键（FilterPageSettingId 等）自动回退迁移；
- 参数页一次调 `paramschema` 拿到模板 UI 包 + 各槽位 values（Block 默认值打底→已保存值→旧键迁移三层合并），保存时按 DSL 白名单重组。
- Seeder 幂等自愈（NOT EXISTS + UPDATE、旧库自动补表补索引），换机器拉代码启动即就绪。

**诚实缺口**：DB 槽位关系当前驱动的是"参数配置页的折叠分组与回填"，运行时模板仍以 `Html.PartialAsync` 硬编码引入三个内置 Block；按 ViewPath 动态解析渲染的通用 BlockHost 未做，HtmlCode/ScriptCode 在线编辑字段已建未消费。

### 8. 其余已落地、值得一提的能力

- **PageGen 三屏自动生成**：选表即生成 Filter/List/Detail 三份 PageSetting 与页面实例，标准 CRUD 零拖拽【已实现】；
- **设计器双模式**：可视化画布与 Markdown 风格 DSL 双向编辑，配置可 Git 对比【部分：边界场景同步/语法校验待加固】；
- **BaseLayout 表单外壳契约**：label/必填星号/说明/布局由统一外壳承担，新组件只写业务【已实现】；
- **多项目数据库隔离**：请求体 project 路由，平台库与业务库端点前缀分离，Block 请求构造收口在一处【已实现】；
- **多桌面壳演示**：Windows / Mac 拟物 / 车机暗黑，内容与壳分离【已实现（演示级）】；
- **模板隔离策略**：一场景一模板（triscreen-blocks / filterlist-crud / tree-detail / detail-modal / crud-basic 等），横向新增而非膨胀单模板【已实现】；
- **Razor 局部视图渲染通道**：PageSetting 支持 RenderMode=Back【已实现】；
- **组件双定义源**：Razor cshtml 定义优先（可版本化、IDE 高亮），DB 元数据兜底供设计器【已实现】。

## 四、短板与风险（按严重度排序，均已核实）

### 1. 安全：当前仅限可信内网，这是生死线

- 启动管线没有任何认证/授权中间件；
- `/api/rpc/eval` 默认开启（`Dyn:Rpc:EvalEnabled` 默认 true），可执行任意 C# 表达式并触达全部 DI 服务与数据库，属于确定的未授权远程代码执行面；
- 管理端设计器入口仅靠配置开关控制可见。

代码注释对这一点是诚实的（"接入鉴权前仅建议内网开发环境开放"），但**对外开放/多人部署前，认证 + 生产默认关 eval 是第一优先级，没有之一。**

### 2. 零自动化测试

挂载竞态、参数层级解析、动作链重解析这类逻辑最依赖回归保护，目前全靠人肉与浏览器验证。历史 bug 记录（孤儿 App、initActions 竞态、幂等挂载）几乎全是时序问题——没有测试，下次重构随时可能回归。

### 3. 完成度断层：设计跑在实现前面

积木 DB 化与运行时硬编码 partial 之间断了一层；规划清单中的组合复用、声明式接线编排、在线 Block 编辑等尚无代码。半成品本身不可怕，可怕的是系统外观暗示"这些都能用"。文档与 UI 上应明确标注现状。

### 4. 可维护性信号

- 前端无 TypeScript、无按需加载/Tree Shaking；dyn-action.js 已约 1300 行；
- 两套 API 信封（code/msg/data 与 success/message/data）并存未统一；
- 根目录散落一次性脚本（fix_*.py、strip_templates.py、check_html.txt 等）、存在"dyn-core - 副本.js"这类需靠纪律禁止编辑的文件、JS 版本号手工 bump；
- 文档存在代差：旧架构文档仍描述已废弃的 msgCenter/双模式。

### 5. 能力边界（原文档已正确列出的部分，维持）

- 免模型 CRUD 仅单表，多表 Join/一对多事务未做；
- 表单联动校验协议（显隐/必填/禁用的规则体系）不系统；
- DSL 双向同步的边界容错、设计器对非开发者的易用性仍需打磨；
- "不锁 UI 库"准确含义是**内核不锁**；官方组件库深度绑定 Element Plus，换库需另实现一套组件，并非开箱可换；
- 移动端是"架构未堵死"的预留状态，当前无移动端组件/模板，不宜表述为"已支持"。

### 提分路径（只做投入产出比最高的三件事）

1. **加认证 + 生产默认关闭 eval**：安全维度 35→60，综合立涨，工作量最小；
2. **给参数链解析与挂载生命周期补最小测试集**：哪怕十几个用例，可维护性 60→75，直接锁住历史时序 bug 不回归；
3. **收口积木断层**：要么实现按 ViewPath 渲染的 BlockHost，要么在参数页/文档明确"当前仅内置三 Block"，消除"看起来都能配"的假象。

三件事完成后，综合分上 85 是现实的。

## 六、最终评价（不吹捧，也不妄自菲薄）

它真正稀缺的不是任何一个单项概念——声明式动作、低代码、UMD、动态 CRUD 都不是新发明——稀缺的是**这套概念被组合得自洽，且在最难的工程细节（多 App 嵌套生命周期、参数跨容器流动、后端动作下发）上真的落地并踩过了坑**。

在开源 .NET 低代码/页面引擎中，"Razor 双范式 + 免模型 CRUD + 强类型 RPC 桥 + 可嵌套独立 App + 统一参数链"这一整套组合，目前未见同等完成度的同类。它不是可以立刻对外卖的产品，但是一个**核心机制达到专业水准、架构方向正确、值得继续长期投入**的自研引擎。

后续迭代最该警惕的也不是"功能不够多"，而是：不要让规划跑得比实现快、不要让系统靠作者记忆维持、在对外开放前先把安全底线补上。
